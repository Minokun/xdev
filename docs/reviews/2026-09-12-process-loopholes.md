# xdev 过程漏洞总审查：缺陷逃逸点的系统性归因（2026-09-12）

> 与 `2026-09-12-tank-postmortem.md` 的关系：那份回答"坦克大战哪三个洞"，本文回答更上一层的问题——
> **这些洞在任意任务类型（API / 数据管道 / 文档 / 算法研究）里长什么样，流程的哪个抽象层该堵**。
> 方法：把三轮实盘（坦克三轮 bug / cronspec A/B 双臂 / xdev 自审计三轮链）的每个缺陷统一按
> "哪道闸本该抓住它、为什么没有"重新归因，只保留**领域无关**的结论。
> 每条漏洞给：抽象层定义 → 实盘证据 → 在非游戏任务里的形态 → 修法方向 → 现状。

## L1 判据集完备性无闸

**抽象层**：xdev 的验证体系是自底向上的——作者写判据 → 闸门验证判据真被执行、真会红。
**"需求/真值 → 判据"这个方向的覆盖审计不存在**。判据表的完备性完全取决于作者想到什么。

**实盘证据**：
- 坦克：123 项测试全绿，但"敌坦方向分布"（真值在 `.research/upstream/REVERSE.md` 的
  `CalcDirToTarget` 表）从未进入判据表——作者设计期把它简化掉了，此后所有闸门对这条维度结构性失明。
- 同会话：子弹渲染形状、暂停可见性，同样不在判据集。
- xdev 自身：B1（探针 harness 接受 pass=0）——"46 条探针全红"的声称在 Node 25 下全是空转，
  因为"harness 读没读到输出"不在任何判据里。

**非游戏形态**：API 项目 = 错误码/分页边界/并发语义没判据；数据管道 = 脏数据形态没判据；
研究流程 = 混淆变量没判据。**任何领域都是同一张空白支票。**

**修法方向**：把"判据从哪来"变成机械产物——需求条目与外部真值条目**逐条三态登记**
（已覆盖→判据编号 / 显式豁免→理由 / 未覆盖），门下门机械核查"未覆盖且无豁免"项。
（即 tank-postmortem 的 P0-1，本文把它从"复刻类"推广为全任务类。）

## L2 参照物锚在未审的解释产物上

**抽象层**：门下门审"计划对设计的忠实度"；对抗审查审"diff 对设计的偏离"；drift check 审
"文档对仓库的漂移"。**所有闸门的锚都是设计文档。但设计文档本身是作者对用户需求的解释——
这个解释从没有被审过。** 解释错了，下游全部闸门会把错误忠实执行到底。

**实盘证据（最有力的一条）**：用户需求是"画面也一样复刻"。设计文档（`2026-09-11-battle-city-design.md:107`）
把它转写成 A7 = "**4 个等级的坦克**渲染结果与权威 CHR 图块表逐像素一致"——只有坦克、只到图块表。
子弹/爆炸/道具/护盾的视觉同一性**在解释层就被丢掉了**。此后：门下门 approve（计划忠实于设计 ✅）、
A7 判据全绿（坦克确实逐像素一致 ✅）、对抗审查无异常（diff 符合设计 ✅）——**每个闸门都正确工作，
用户要的却没交付**。爆炸颜色的"SP3 调色板"取舍同构：忠实于上游参考实现，而不是忠实于用户记忆里的原版。

**非游戏形态**：用户说"要快"→ 设计成"加缓存"→ 全部闸门验证缓存正确——但用户的意思是"首屏 2 秒内"。
**需求是体验/结果，设计是机制/实现，中间的解释层是全流程唯一没有闸门的位置。**

**修法方向**：阶段 1 增加**需求逐条映射表**（每条用户需求 → 设计条款编号 → 判据编号），
门下门加一维"需求覆盖"审查（与"计划忠实于设计"并列）；解释性收窄（"画面复刻"→"图块一致"这种）
必须显式标注并给用户确认。注意这与 A4 的"事实性前提例外"不同：那条管外部世界断言的真假，
这条管需求解释的完整性。

## L3 计算独立 ≠ 信息独立

**抽象层**：xdev 的审查独立性是"fresh 会话、不继承上下文"——**计算独立**。
但审查材料（diff、设计文档、判据表）全部由被审者准备。审查员看不到作者没给的东西。
信息源同源 → 作者的盲区就是审查的盲区。

**实盘证据**：坦克对抗审查抓了假证据、死模块（材料内的不一致，表现出色），但"子弹看起来不对"
结构性地抓不到——它需要**材料外的感知**（看一眼渲染结果 / 读 ROM 真值表），材料里没有。
xdev 自审计链里，三轮审计能互相抓错（A1c 假阳性、双 node 二进制），恰恰因为审计者们**各自独立
跑了命令**——信息源不同源。这是正反两面的实证。

**非游戏形态**：代码审查只拿到 PR diff，不看生产数据/真实流量/上游契约原文。

**修法方向**：审查员的输入清单里强制包含**作者无法控制的信息源**——外部真值原文（L1 的清单）、
真实运行产物（跑出来的东西，不是描述的）、用户验收记录（L5）。规则表述："审查材料必须含至少一份
未经被审者加工的一手源"。

## L4 增量轮闸门衰减

**抽象层**：首轮交付走全密度闸门（面板+门下门+对抗审查+探针+E2E），修复/迭代轮走 bugfix
的轻流程。但增量轮改的往往是**共享基础设施**（取表层、输入层），爆炸半径比首轮新代码更大。
风险与闸门密度倒挂。

**实盘证据**：坦克 T3 修复轮改取表层 → 自造砖墙回归（负数索引约定废除未扫类），靠目视截图才发现；
T5→T6 零改动——"所有坦克不能左右移动"是修复轮交付时带着的存量，"四方向可动"只在出生点特定
场景验过。bugfix.md 只要求"全量测试"，探针重跑与受影响 E2E 都不强制。

**修法方向**：bugfix.md 的 S2/S3 增加：触及"被 ≥2 处复用的共享层"时强制同类扫描 + 探针重跑 +
受影响面 E2E；每轮交付声明**本轮改动的影响面清单**（谁 import 了被改的文件）。

## L5 用户验收不沉淀为基线

**抽象层**：用户亲手玩过/验过的行为，是**最高价值的回归判据来源**——但流程没有
"用户验收 → 冻结为判据"的钩子。下一轮改动可以静默破坏用户已经认可的东西。

**实盘证据**：T3 用户验过"能玩"，T5 交付就出了"四方向可动"存疑的回归窗口；cronspec 两轮之间同理。
砖墙回归本质是"首轮已被目视确认的画面被修复轮破坏"。

**非游戏形态**：API 的已上线契约、报表的已确认数字、文档的已发布承诺——被破坏时没有任何闸门报警。

**修法方向**：阶段 4 交付后，把"用户确认过的行为"转成判据回填进判据表（哪怕只是冒烟级）；
流程上把"用户验收"当成一种**真值源**对待（喂给 L1 的清单）。

## L6 验证有效性无反馈环

**抽象层**：审查员有命中率台账（review-ledger，连续 5 次零命中降级）——但**判据和探针没有**。
哪条判据历史上抓到过真缺陷、哪条从来没红过、哪条探针一直空转，流程不知道，也就回答不了
A/B 实验暴露的那个问题："这些闸门值不值 18.2× 的成本？"

**实盘证据**：坦克三轮里真正抓住用户级 bug 的全是**事后临时写的取证**（240k 帧 soak、足迹断言、
逐字节帧比对）——预写判据的贡献率问题没有任何数据面。cronspec A/B：Q 判据对两臂打平，
因为 prompt 预告了陷阱——如果判据有效性有台账，"这类判据在这类任务上从不区分"早该可见。

**修法方向**：判据级台账（每条判据：红过几次、其中真缺陷几次、变异探针覆盖它没）；
交付报告加一行"本轮判据抓获记录"。这是 review-ledger 的同构扩展。

## L7 "全绿"语义跨轮漂移

**抽象层**：每轮交付的"全绿"= 当轮判据集全绿。轮次之间判据集会增删改，于是两个轮次的"全绿"
不是同一个命题。用户听到的"全绿"在语义上漂移。

**实盘证据**：坦克首轮 98 项 → 修复轮 123 项 → 再修后更多；每轮都声称"全绿"，
但 T6 的 bug 在所有这些"全绿"里都是绿的——因为它不在任何一轮的判据集里。

**修法方向**：交付报告的验证读数必须带**判据集哈希/计数与 diff**（"本轮判据集较上轮 +5/-1"），
让"全绿"成为可比较的对象。（与 L5/L6 共用基础设施。）

## L8 元漏洞：用加规则修规则失效

**抽象层**：本仓库的历史模式——失效 → 加规则/加审查员 → 体量涨 → 遵守率降 → 再失效。
审计 F2 已确诊（full-dev.md 270→513 行、persona 翻倍；"实盘失效多为规则没被执行"）。
**本文档的 L1–L7 修法如果不带执行机制，就是把同一个病再犯一遍。**

**修法方向**：每条新规则必须带它的**机械执行体**（脚本/探针/drift claim/gate 脚本槽位），
否则不进文档；每条新规则进文档时必须删掉或合并一条等价的旧 prose（体量预算制）；
v3.1.1 的 B1 教训常态化：守卫本身必须有变异探针。

## 与已落地修复的对账

| 漏洞 | v3.1.1 / v3.2 / v3.3 前置修了吗 |
|---|---|
| L1 判据完备性 | ❌（tank-postmortem P0-1 是其任务级形态，未实现） |
| L2 解释层无闸 | ❌（本文新提出） |
| L3 信息独立 | ❌（本文新提出） |
| L4 增量轮衰减 | ❌（tank-postmortem P1-1，未实现） |
| L5 验收基线化 | ❌（本文新提出） |
| L6 有效性反馈环 | 🔶 审查员有台账；判据/探针没有 |
| L7 全绿语义漂移 | ❌（本文新提出） |
| L8 元漏洞 | 🔶 诊断在案（F2），无机制 |

已修的那批（门禁可达性、守卫自证、测量错对象、写面归属、等待语义）属于**"机制写了没接线"**层——
它们让已存在的规则变得可执行。本文的 L1–L7 是更上一层：**流程的视野里根本没有这些东西**。
两层都真，别混淆：接线修复不替代视野修复。

## 建议落地顺序（考虑 L8 的体量约束）

1. **L1+L2 合并落地**（一张"需求/真值 → 判据"映射表同时堵两个洞，门下门加一维机械核查）——
   这是全部漏洞里杠杆率最高的，且执行体（表格+脚本核查）便宜。
2. **L3** 改审查 prompt 契约（材料必须含一手源）——文案级。
3. **L4+L5** 进 bugfix.md / 阶段 4——各一条机械规则 + 一个探针。
4. **L6/L7** 复用 review-ledger 基础设施，增量做。
每条都必须自带执行体与变异探针，否则不写进文档（L8 的纪律）。
