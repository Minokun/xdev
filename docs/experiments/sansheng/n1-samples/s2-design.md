# demo-app 库存扣减 · 设计文档

版本：v0.1　状态：待评审　项目代号：demo-app

## 1. 背景与功能描述

demo-app 是一个电商下单演示服务。用户在前台选择 SKU 下单，系统在生成订单的同时扣减该 SKU 的可用库存。库存是有限的共享资源：同一 SKU 可能被大量用户同时抢购，一旦扣减逻辑存在并发漏洞就会"超卖"——成交数量超过实际库存，导致无法履约、赔付与客诉。因此本子域的核心诉求有二：一是**并发防超卖**，任何并发压力下同一 SKU 都不超卖；二是**库存流水**，每次库存变动都留下可追溯的记录，支撑对账、审计与售后。

本功能以 REST JSON API 的形式对外提供以下能力：

1. **下单**：提交 skuId 与购买数量，生成订单并扣减库存；
2. **库存扣减**：按数量扣减 SKU 可用库存，库存不足时整单失败；
3. **库存流水**：每次变动写入一条流水，记录变动前后库存与来源单据；
4. **库存查询**：返回 SKU 实时库存，高频读取经 Redis 缓存加速。

技术栈：Python + FastAPI + SQLAlchemy + PostgreSQL + Redis；Alembic 管理迁移，pytest 负责自动化测试。本期仅覆盖"下单即扣库存"一种模式，取消回补、支付等上下游环节不在范围内（见第 3 节非目标）。

## 2. 核心需求（功能点）

### F1 并发防超卖：同一 SKU 并发下单不超卖
- 本功能的最高优先级功能点。任意并发度下，同一 SKU 成功扣减的总量不得超过其可用库存；任何时刻、任何读路径下库存不得出现负数。
- 库存恰好扣减到 0 是合法终态；此后所有请求一律按库存不足处理。
- 不允许部分成交：请求数量超过剩余库存时整单失败，库存保持不变。

### F2 库存扣减
- 下单成功即扣减，扣减数量 qty 必须为正整数。
- 扣减与订单生成在同一事务内提交：任一步失败整体回滚，不允许"扣了库存但订单未生成"或反向的中间状态。
- SKU 不存在时返回 404。

### F3 下单接口
- `POST /api/orders`，请求体 `{"skuId": 1, "qty": 2}`。
- 成功返回 201 与 `{orderId, skuId, qty, status}`；库存不足返回 409 与错误码 `INSUFFICIENT_STOCK`；参数非法返回 422。

### F4 库存流水
- 每次库存变动写入一条流水：`sku_id`、`change_qty`（出库为负）、`before_stock`、`after_stock`、`ref_type`（本期固定 `order`）、`ref_id`（orderId）、`created_at`。
- 流水只增不改，不提供更新与删除入口；提供 `GET /api/skus/{id}/flows` 按时间倒序分页查询。

### F5 库存查询
- `GET /api/skus/{id}/stock` 返回 `{skuId, stock}`。
- 读取采用 cache-aside：先查 Redis，未命中回源数据库并回填；扣减成功后同步失效对应缓存键，保证查询读到最新值；Redis 故障时降级直读数据库，不阻塞查询与下单主链路。

### F6 库存不足处理
- 库存不足时返回 409 与 `INSUFFICIENT_STOCK`；库存值、订单数、流水数与请求前完全一致（零副作用）。

## 3. 非目标

- **不做多仓库/多货主库存**：单仓单库存模型。
- **不做库存预占**：下单即扣减，不处理预占、锁定与解冻。
- **不做取消回补与退款**：取消订单的库存回补留待后续版本，本期取消场景人工调账。
- **不做营销玩法**：秒杀、限购、排队等上层能力不在本期。
- **不做预警与盘点**：低库存预警、补货建议、盘盈盘亏不涉及。
- **不做请求级幂等去重**：重复提交由调用方防重，本期服务端不承诺幂等。
- **不提供 Web UI**：仅暴露 REST API。

## 4. 约束

- 技术栈：Python ≥ 3.11、FastAPI、SQLAlchemy 2.x、PostgreSQL ≥ 14、Redis ≥ 6；数据库变更一律经 Alembic 迁移执行，不允许手工改表。
- **扣减原子性**："判断库存充足"与"实际扣减"必须作为一个不可被并发事务穿插的整体执行，由数据库层保证（事务 + 行级锁或等价的原子条件更新），不允许出现"先查出来、判断通过、再写回"的分离窗口；库存字段只允许通过扣减服务修改。
- **账实一致**：每笔成功扣减对应且仅对应一条流水；流水的 before/after 与库存终值必须能相互印证。
- 性能：演示环境下单接口在单 SKU 100 并发时 p95 < 500ms；库存查询默认命中缓存。
- 时间：存储与接口统一使用 UTC，ISO 8601 格式。
- 验证以真实命令为准：自动化用 `pytest`，接口行为用 `curl` 实测，禁止仅以人工目测代替验证。

## 5. 验收标准

| 功能点 | 验收标准 |
|---|---|
| F1 | SKU 库存初始化为 50，100 个并发请求各购 1 件：成功订单恰好 50 笔，最终库存为 0，全程无负库存，流水恰好 50 条且相邻 before/after 首尾衔接 |
| F2 | 库存 10 扣减 3 后库存为 7；qty 为 0/负数被 422 拒绝且数据零变更 |
| F3 | 合法请求返回 201 且响应含 orderId；库存不足返回 409 与 INSUFFICIENT_STOCK |
| F4 | 任意一笔扣减可查到唯一对应流水，before/after/orderId 正确；流水无更新/删除入口 |
| F5 | 扣减后立即查询返回值与数据库一致；连续二次查询命中缓存；Redis 停用时查询降级可用 |
| F6 | 库存不足请求执行后，库存、订单、流水与请求前完全一致 |

## 6. 风险与开放问题

- 本期单实例单库部署，数据库层并发控制即可满足 F1；未来若多实例或多库拆分，一致性方案需重新评估。
- "下单即扣"模式下取消订单会造成库存缺口，回补能力依赖后续版本，需在运营流程上先行约定。
- 流水随业务量增长，后续需补归档与清理策略；查询接口的分页上限需随数据量调整。
