## Problem Statement

现在的推文选题入口分成“智能模式”和“手动模式”，但实际信息源太少，手动模式主要还是围绕澎湃科技、SOTA 开源项目、实时新闻、新浪直播这四个方向在转。随着用户量上来，这种结构会把同一批热点反复喂给不同用户，最后产出的文章内容越来越像。

这次改动的目标不是重做整套生成链路，而是把“选题前置层”重做：先接入尽可能多的信息源，再根据用户关注话题让 LLM 主动挑出最相关的内容，并按会员等级控制最终返回的选题数量。后面还是走现在的生成模式，把这些选题继续生成成内容。

## What Makes This Cool

用户不再是在“选哪个源”上做决定，而是在“要系统帮我从整个信息池里挑出什么”上获得结果。

这会让两个事情同时变好：

- 重复内容会下降，因为同一个用户、不同用户、不同等级看到的候选池不再一样。
- 入口会更像“推荐系统”，而不是一个信息源切换器。

## Constraints

- 现有异步任务历史不能断，提交后依然要可追踪 `pending/running/completed/failed`。
- 现有 `tweet_topics` 的生成结果结构要尽量兼容，不然前端历史页会被迫一起重写。
- 会员等级要进入选题数量控制，目标规则是 `free = 3`、`pro = 5`、`ultra = 10`。
- 会员等级和最终数量必须由后端通过 `TierService` 计算，不能信任前端传入的 tier 或 job payload。
- 新逻辑必须复用现有后台生成模式，不引入第二套内容生成链路。
- 需要继续支持已保存主题和自定义主题，但它们应该成为“推荐上下文”，而不是唯一入口；没有主题时也必须能走热点优先推荐。
- 需要把更多信息源纳入统一池，包括现有四个源、热点资讯源，以及后续容易扩展的其他来源。
- LLM 只能选择服务端提供的候选 ID，最终 URL 必须由服务端从候选池映射，不能保存模型自由生成的链接。

## Release Scope

### In Scope

- 统一选题层用于 async 推文选题提交和 worker 执行。
- 现有四个新闻源和五个热点源进入 v1 统一池。
- `free / pro / ultra` 只控制最终返回数量，不改变信息源可见性。
- 手动模式在 v1 保留，但降级为“高级源筛选”，不再是主入口。
- 现有历史页、job 状态、生成结果结构继续兼容，老记录也必须能读。

### Out of Scope

- 重写文章生成链路。
- 新建独立任务中心或通知中心。
- 删除手动模式。
- 重新设计会员订阅、支付或配额系统。

### News sources

- SOTA 开源项目
- 实时新闻
- 新浪直播

### Hotspot sources

- baidu
- weibo
- douyin
- thepaper

### Deferred until later

- 任意新的外部源都先接入 source registry，再决定是否纳入默认池。
- 不在 v1 里做“无限源自动接入”，避免变成不可控的抓取洪水。
- 不在 v1 里做全站跨用户去重，先用更大的统一池和同一用户历史去重降低重复。

## V1 Budget and Fallbacks

- 每个新闻源默认抓取 15 条，每个热点源默认抓取 20 条。
- 单个源抓取超时为 12 秒，最多 4 个源并发抓取，避免 worker 被外部站点拖死。
- Phase 1 fetch budget: 60 秒内拿到统一池的可用数据；超过就停止继续抓取。
- 单次统一池的初始候选上限为 160 条，超出先做标题和 URL 去重，再交给 LLM 筛选。
- LLM prompt 最多放入 80 条候选，每条候选只保留 title、source、url、summary、heat 五类字段。
- Phase 2 LLM budget: 90 秒内完成相关性筛选和一次重试；第二次仍解析失败就进入 fallback。
- Phase 3 persistence budget: 15 秒内完成 job 更新和 history 落库。
- worker 目标完成时间控制在 180 秒内，超时则走失败态，不继续追跑。
- 提交前必须做 per-user active job cap 和基础请求限流；限流失败不创建 job、不入队。
- 单个源失败不应拖死整个任务，只要还有可用源，任务就继续。
- fallback 条件包括：LLM 空响应、JSON 解析失败、筛选后结果少于 tier 目标数量的 50%。
- fallback 排序顺序是：标题命中关注话题关键词 > 热点热度 > 发布时间新旧 > source registry 顺序。
- 如果所有源都没有数据，任务失败并返回用户可读错误。

## User States

- `pending / running`：显示“后台推荐中”，允许用户离开页面。
- 没有关注话题：自动退回到热点优先推荐，不阻塞提交。
- 关注话题很弱或筛完没有强相关结果：如果 LLM 相关结果少于 tier 目标数量的 50%，走热点优先 fallback，并在 job 详情里记录原因。
- tier 返回数量超出上限：直接截断到 `3 / 5 / 10`，不让前端再做二次裁剪。
- 某些源部分失败：仍可完成任务，但在结果里标明“部分源失败，已用可用数据完成推荐”。
- 手动模式在主界面不再作为并列 tab 出现，只作为高级筛选面板里的 source filters。

## Premises

1. 重复内容的根因是信息源过窄，而不是生成模型本身。
2. 统一的推荐层比继续扩充手动模式更能解决规模化重复问题。
3. 会员等级最适合控制的是“返回多少个选题”，而不是“让用户能看到多少源”。
4. 现有异步任务、历史记录和生成链路是正确的 backbone，应该保留。
5. 用户关注话题是最值得让 LLM 介入的过滤信号。
6. v1 只做同一用户的历史去重，不做全站跨用户去重。

## Approaches Considered

### Approach A: 扩展现有模式

保留手动 / 智能两个入口，只把两边都扩到更多信息源和热点源，再在智能模式里叠加用户关注话题筛选与会员限额。

- Effort: S
- Risk: Med
- Pros:
  - 改动最小，能最快把“源太少”这个问题压住。
  - 现有页面、路由和 worker 只需要局部扩展，不用重做协议。
  - 适合先验证新源是否真的能显著降低重复。
- Cons:
  - 入口仍然会像“源选择器”，长期心智还是偏旧。
  - 规则会继续散在多个地方，后面加源会越来越脏。
  - 解决的是症状，不是完整的产品结构问题。
- Reuses:
  - `backend/api/routes/tweet_topics.py`
  - `backend/api/workers/tweet_topics_worker.py`
  - `backend/api/services/topic_selector.py`
  - `frontend/src/app/tweet-topics/components/ManualMode.tsx`
  - `frontend/src/app/tweet-topics/components/IntelligentMode.tsx`

### Approach B: 统一选题层

新增一个统一的选题推荐层。它先汇聚所有信息源和热点源，再结合用户关注话题做 LLM 相关性筛选，最后按会员等级返回固定数量的候选选题。前端只需要表达偏好和结果，不再暴露底层源细节。

- Effort: M
- Risk: Med
- Pros:
  - 入口更清晰，用户看到的是“推荐多少个选题”，而不是“从哪个源抓”。
  - 后续加新源只要接进推荐层，前端和 worker 协议基本不用再动。
  - 最容易把“重复”这个问题收口到一个可调的地方。
- Cons:
  - 前后端都要重新对齐一次接口和响应结构。
  - 需要兼容现有 async job 历史页，设计时要更小心。
  - 推荐层会成为新核心模块，需要更明确的边界和测试。
- Reuses:
  - `backend/api/services/topic_selector.py`
  - `backend/api/services/hotspots_service.py`
  - `backend/api/services/tier_service.py`
  - `backend/api/routes/tweet_topics.py` 的 async job 流
  - `backend/api/repositories/tweet_topics.py`

### Approach C: 推荐流重做

把推文选题入口重做成默认推荐流。手动模式降级成高级筛选或高级开关，主要让用户选择偏好，而不是选择来源。

- Effort: L
- Risk: High
- Pros:
  - 体验最顺，用户不会再被源选择困住。
  - 最有利于后面做个性化、分层推荐和内容去重。
  - 对“选题系统”这个产品形态最完整。
- Cons:
  - UI、接口、历史页和文案都要一起重构。
  - 周期长，风险高，不适合这轮先验证重复问题的场景。
  - 容易把当前稳定链路改散。
- Reuses:
  - `backend/api/services/topic_selector.py`
  - `backend/api/routes/tweet_topics.py`
  - `frontend/src/app/tweet-topics/page.tsx`

## Recommended Approach

采用 Approach B：统一选题层。

原因很直接：这次的根因不是“再多加几个按钮”，而是“选题入口本身就应该从源选择器升级成推荐层”。B 能把所有信息源、热点源、用户关注话题和会员等级放到同一个决策面里，同时还保留现有异步任务和历史记录体系。主界面只保留推荐流，手动选源能力放到高级筛选面板。它比 A 更像长期解法，又比 C 小一档风险，适合现在这轮改造。

## Open Questions

- 高级筛选面板默认是否展开，还是只作为折叠区存在。

## Contracts

### Submit request

现有 async 提交接口继续作为入口，但请求会被归一成统一推荐参数：

- `topic_id` / `custom_topic` / `topic_description`：推荐上下文，全部为空时表示热点优先推荐，不再拒绝提交。
- `save_topic`：是否写入用户主题库；只有自定义主题非空时生效。
- `topic_count`：用户显式请求数量，先校验范围，再由后端读取会员等级截断到最终数量。
- `source_filters`：可选高级筛选，只在高级面板里出现；进入 worker 前必须归一成 source registry ID。

### Async job payload

`tweet_topic_jobs.request_payload` 记录规范化后的请求，至少包含：

- `mode`
- `topic_context`
- `source_filters`
- `tier`
- `requested_topic_count`
- `effective_topic_count`
- `source_registry_version`

Validation precedence:

1. Reject or throttle before creating a job if the user already has too many active tweet topic jobs or exceeds request-rate policy.
2. `requested_topic_count` must be coerced into a supported numeric range before tier logic runs.
3. `tier` must be read from `TierService.get_user_tier(user_id)` on the server, never from client input.
4. `effective_topic_count = min(requested_topic_count, tier_cap)`.
5. If the request omits `topic_count`, use the mode default first, then tier cap second.
6. free/pro/ultra caps are always `3 / 5 / 10`; superuser follows ultra cap in this feature.
7. The worker must use `effective_topic_count` for final truncation and treat legacy jobs without it as `topic_count` compatibility mode.

### Job result

`tweet_topic_jobs.topics_data` 继续保持现有兼容字段，并增加一个可选的 `recommendation_meta`：

- `filtered_news`：与主题最相关的候选新闻/热点。
- `topics`：最终选题列表。
- `summary`：整体总结。
- `hot_keywords`：热门关键词。
- `recommendation_meta.selected_sources`：实际使用的源。
- `recommendation_meta.fallback_reason`：为空或 fallback 时的原因。
- `recommendation_meta.tier_cap`：free/pro/ultra 最终截断值。
- `recommendation_meta.source_failures`：部分源失败信息。
- `recommendation_meta.requested_topic_count`：用户请求数量。
- `recommendation_meta.effective_topic_count`：后端 tier 截断后的最终数量。

LLM selection contract:

- 交给 LLM 的每条候选必须带稳定 `candidate_id`。
- LLM 返回只能引用 `candidate_id`，不能自由生成 `source_urls`。
- `topics[*].source_urls` 由服务端根据 `candidate_id` 回填，只允许候选池里的 `http/https` URL。

### Backward compatibility

- 现有前端如果只读 `topics`、`summary`、`hot_keywords`，仍然可用。
- `filtered_news` 和 `recommendation_meta` 都是渐进增强字段，不作为旧页面的硬依赖。
- job 列表和详情接口继续返回 `record_id`、`status_url`、`news_urls`、`error_message` 这些老字段。

## Rollout and Compatibility

- `request_payload.source_registry_version` 从 `v1` 开始写入；旧记录没有该字段时按 `legacy` 处理。
- 旧记录没有 `recommendation_meta` 时，接口返回 `recommendation_meta: null`，前端不展示推荐解释区。
- 旧记录的 `news_source = all` 继续显示为“全部来源”，不会反推具体 source registry。
- 旧记录的 `topic_count` 继续按数据库原值展示，不套用新的 tier cap 重新裁剪。
- 新记录必须写入 `effective_topic_count`，历史页展示最终数量时优先读它。
- 新记录的推荐源名称必须使用 registry ID；展示文案再映射成人类可读名称，避免 `SOTA 开源项目` / `SOTA开源项目` 这类名称漂移。
- 旧记录不迁移数据，只做读取兼容，避免改写已有历史结果。

## Tier Count Matrix

| Tier | Default request | Tier cap | Effective result |
|------|-----------------|----------|------------------|
| free | 10 | 3 | 3 |
| pro | 10 | 5 | 5 |
| ultra | 10 | 10 | 10 |
| superuser | 10 | 10 | 10 |

If a user explicitly requests fewer than the cap, keep the smaller number. If a user requests more than the cap, clamp to the cap.

## Success Criteria

- `free` 用户每次最多拿到 3 个选题，`pro` 5 个，`ultra` 10 个。
- 用一组固定 fixture 跑 3 次推荐时，至少能同时覆盖新闻源和热点源，且不会在同一批结果里重复同一标题。
- 对同一个保存主题，连续两次生成的候选标题重合度明显低于当前实现。
- 用户关注话题为空时，推荐层可以稳定退回到热点优先。
- 历史页、任务状态和现有生成链路继续工作，不需要用户重新学习一套新流程。
- LLM 解析异常或提示注入不能把非候选池 URL 写入 `topics[*].source_urls`。
- 用户重复提交超过 active job cap 或请求限流时，不创建后台 job，并返回可读提示。

## Next Steps

1. 把现有新闻源、热点源和未来扩展源整理成统一的 source registry，并把 route 中的抓取/URL 辅助逻辑抽到 service 层。
2. 抽出一个推荐服务，先做“抓取 + 聚合 + LLM 相关性筛选 + tier 数量控制”，依赖 fetcher、LLM、tier service 可注入。
3. 让 async tweet topic worker 直接调用这个推荐服务，保持现有 job 历史结构。
4. 在 async submit 阶段加入 active job cap、请求限流、空主题热点 fallback 和 `effective_topic_count` 写入。
5. 再调整前端，把主入口收敛成推荐流，并把手动模式降级为高级筛选。
6. 补上针对源覆盖、tier 数量、URL 回填安全、fallback、部分源失败和重复抑制的测试。

## Visual Design Specs

### Direction

推文选题页从“双模式工具页”变成“推荐控制台”。主视觉应该强调系统正在替用户从更大的信息池里筛选，而不是让用户先做源选择。整体方向保持当前产品的卡片式风格，但入口层级要更果断：推荐表单是主角，高级筛选是辅助。

### Component Hierarchy

1. `RecommendationHero`
   - 显示“根据你的关注话题，从全网信息池推荐选题”。
   - 展示当前会员等级和本次可生成数量：free 3、pro 5、ultra 10。
   - 如果用户没有关注话题，提示“将使用热点优先推荐”。
2. `TopicContextSelector`
   - 合并现有已保存主题选择、自定义主题输入、保存主题选项。
   - 主题描述作为可选增强项，不作为必填。
3. `RecommendationControls`
   - 默认只展示生成按钮、目标数量说明和推荐范围说明。
   - 不再展示四个并列新闻源卡片。
4. `AdvancedSourceFilters`
   - 折叠面板，承接原手动模式能力。
   - 允许用户选择 news sources 和 hotspot sources，但文案应是“限制推荐范围”，不是“手动模式”。
5. `GenerationStatusCard`
   - 复用现有 async job 状态，但文案从“生成中”调整为“推荐并生成选题中”。
6. `HistoryView`
   - 保持现有列表结构。
   - 如果 `recommendation_meta` 存在，展示使用源数量、部分源失败提示、fallback 原因。

### Interaction States

- Default：展示主题选择、会员数量、主按钮和折叠的高级筛选。
- Loading topics：主题下拉显示 skeleton 或 disabled 状态，主按钮不可提交。
- Empty topics：允许直接输入自定义主题，也允许不填主题走热点优先。
- Submitting：主按钮进入 loading，页面顶部出现 `pending` 状态卡，用户可离开页面。
- Running：状态卡显示“正在抓取多源资讯 → 正在筛选相关内容 → 正在生成选题”的三段式进度文案。
- Completed：历史列表首条高亮一次，结果卡展示推荐来源和选题数量。
- Partial success：如果部分源失败，显示轻量 warning：“部分来源暂不可用，已使用可用数据完成推荐”。
- Fallback：如果进入热点优先 fallback，展示说明：“关注话题相关内容不足，本次优先使用热点趋势”。
- Failed：复用现有错误卡，但 CTA 是“重新推荐”，不是“重新生成”。

### Responsive Behavior

- Desktop：左侧是推荐配置，右侧是当前任务/最近历史摘要；历史列表仍在下方或右侧区域延展。
- Tablet：推荐配置和状态卡上下堆叠，高级筛选保持折叠。
- Mobile：只保留单列流，会员数量提示紧贴主按钮；高级筛选默认折叠且放在主按钮下方。

### Accessibility

- 高级筛选必须是可键盘展开的 button，不使用纯 div click。
- 生成状态变化通过 `aria-live="polite"` 通知。
- 部分失败和 fallback 提示不能只靠颜色区分，必须有文本说明。
- source filter 多选项需要明确 checked 状态和可读 label。
- 提交按钮 disabled 时要有相邻文本解释原因，例如“请等待当前任务完成”。

## What I noticed about how you think

- 你没有停在“加几个新源”，而是直接点出了“用户一多后重复文章内容就会很多”，这是在抓规模化问题，不是修局部体验。
- 你把“free / pro / ultra”直接和选题数量绑起来了，这说明你在用会员层级做产品节流，而不是只做文案包装。
- 你明确说“接入我们所有的信息源”，说明你要的是一个统一池，不是再堆几个孤立入口。
- 你最后说“之后再按现在生成的模式去生成选题”，说明你要保留已经验证过的生成链路，只改前面的决策层。
