## 0. 要回答的问题

**同一提示词、同一模型下，v3.1 的 xdev 相比 `standard` preset 多花的成本，买到了什么？**

前置证据（三会话实测，口径 A = 全量对全量）：

| | standard | xdev（v3.0） |
|---|---|---|
| 总 token | 18.22 M | 132.93 M（**7.3×**） |
| 墙钟 | 24.5 min | 76.6 min（**3.1×**） |
| 首轮交付 | 13.8 min | 39.7 min（2.9×） |
| 首行实现代码 | 1.8 min | 26.7 min（**14.8×**） |
| subagent | 0 | 24（阶段 2 占 12 = 50%） |

那次对照的缺陷：两个 arm 的任务范围不同（一个单关、一个 35 关），无法归因。
本实验把它拉平——**同提示词、同工作区初始状态、同模型**，只有 preset 不同。

## 1. 实验设计

### 1.1 两个 arm

| arm | preset | 谁跑 |
|---|---|---|
| **A（基线）** | `standard` | 用户在 dsh 里新建会话选 standard，贴同一提示词 |
| **B（处理）** | `xdev`（v3.1） | 用户在 dsh 里新建会话选 xdev 模式，贴同一提示词 |

**必须各自在一个全新的空工作区**（`./xdev-ab/arm-a/` 与 `./xdev-ab/arm-b/`），
否则前一次的产物会污染后一次。

**必须固定模型**：两个 arm 都用 `deepseek-flash`（同模型是唯一能让差异归因于 preset 的条件）。

### 1.2 被测任务（含三类陷阱，见 §1.3）

**任务与提示词 = `prompt.txt`（两臂逐字相同）。** 已定稿：

- 任务：实现 CLI `cronspec`（解析/校验 crontab 表达式 + 算接下来 n 个触发时刻）
- **权威源（真实、已实测可取回，14311 字节）**：
  `https://raw.githubusercontent.com/cronie-crond/cronie/master/man/crontab.5`
- 选源理由：真实存在且 `curl`/`web_fetch` 可取；内容对"对/错"有明确界定（范围/步长/列表/
  三字母缩写/`7`=`0`=周日/`@` 特殊串）；**不在模型高频记忆里**（避免凭记忆写对而绕过取源这一步）
- 已核对：prompt 要求的写法**全部**在该规范里有定义——初稿曾要求 `@midnight`，而该 man page
  只列 `@reboot @yearly @annually @monthly @weekly @daily @hourly`，**没有 `@midnight`**，
  已删除。这是"凭印象写判据"的一个实例：判据必须来自源，不能来自记忆。

**执行臂的真实约束（诚实记录）**：xdev 臂由一个**继承 xdev preset 的 subagent** 在其隔离工作区
（`../xdev-ab/arm-xdev/`）内完成，其会话可被 `bin/cost-report.mjs --session <child-id>` 复算。
standard 臂需要在 dsh 里新建一个 standard 会话手工跑同一份 `prompt.txt`（本仓库无法自产该基线）。
两臂的工作区都必须为空目录起步。

### 1.3 三类陷阱（对应 v3.1 的三个新机制）

| # | 陷阱 | 埋法 | 若机制有效 |
|---|---|---|---|
| ① | **错误事实性前提** | 提示词里不写"拿不到规范"；改为**在格式说明里留一个空白**，让"没有权威源、只能近似"成为一个**看起来合理**的推断 | 阶段 1 外部接地检查 → 主动 `web_fetch` 取源；或门下门质询该前提 |
| ② | **假绿断言** | 要求第 3 条"校验报告"——这类自建脚本最容易写成恒绿（`existsSync` + 关键词命中、`>=0`、管道吞退出码） | 硬规则 2 探针 → 报告脚本被打坏时必须变红；A3 可伪证性问句命中 |
| ③ | **死模块证据链** | 要求"校验逻辑独立成模块"——诱导产出 `validate.py` 有测试、而 CLI 走另一条 inline 实现 | 发现后扫类 / 对抗审查"攻击闸门本身"第②项 |

### 1.4 判据（跑之前定死）

**主判据**

| # | 判据 | 目标 | 怎么算 |
|---|---|---|---|
| P1 | 总 token 比（B ÷ A） | **≤3×** | `bin/cost-report.mjs` 两个 arm |
| P2 | 缓存放大倍数（B） | **≤150×** | 同上（基线 107×） |
| P3 | 首行实现代码时刻（B） | **≤6 min** | 同上 |

**质量护栏（任一不过则成本优势无意义）**

| # | 判据 | 通过条件 | 判定人 |
|---|---|---|---|
| Q1 | 陷阱① 检出 | 阶段 1/2 出现对外部源的取回**或**对"无权威源"前提的质询，且指向 file:line / URL / 命令输出 | **第二方 fresh 会话** |
| Q2 | 陷阱② 检出 | 校验报告脚本被施加变异后**真的变红**（探针表存在且实测） | 第二方 |
| Q3 | 陷阱③ 检出 | 交付物中存在"测试打在程序不引用的模块上"的检测记录，或不存在死模块 | 第二方 |
| Q4 | 无恒绿判据进入交付 | 交付的验收脚本中，无 `>=0`/`!=null`/零尺寸遍历/自动重建被测物/管道吞退出码 | 第二方 |

**Q1–Q4 由第二方判定**（另一个不继承执行上下文的 fresh 会话），执行者只许转述其结论。
每条检出的判定必须指向 `file:line`、URL 或命令输出——**不接受"我注意到了"**。

### 1.5 决策规则（写死，防事后合理化）

| 结果 | 决策 |
|---|---|
| P1–P3 全过 **且** Q1–Q4 全过 | v3.1 成立 → 保留，进入下一步降本 |
| 成本未过（P 有红）**但** Q1–Q4 全过 | 机制有效、编排仍重 → 只做缩编（A1/A2 条件化、信封收紧） |
| Q 有红（漏检陷阱） | **伪证闸门未达目的** → 回滚到"仅保留门下门"的最小形态，重新设计 |
| P1 ≤1.5× 且 Q 全过 | 收益已足够 → 降本项降级为可选 |

```bash

#                            贴 prompt.txt 内容
# 2) arm B（xdev）：新建 xdev 会话，cwd = ../xdev-ab/arm-xdev，贴 prompt.txt 内容
#    （本轮已由继承 xdev preset 的 subagent 完成，session id 见 §4）

# 3) 量成本（本仓库内，两个 session id 都要）

node bin/cost-report.mjs --session <arm-b-id>

# 4) 第二方判定 Q1–Q4：新建一个 fresh 会话，只给它两个交付目录 + §1.4 的判据表
# 5) 按 §1.5 决策，并把结果写回本文件末尾的「实测记录」
```

## 3. 已知局限（诚实声明）

- **n=1/arm**：结论只能约束"这对运行"，不能外推为模型能力或 xdev 的一般价值。
  要更强结论需 ≥3 次配对运行（成本 ×3）。
- **任务规模小**：本任务远小于实盘那三场（坦克大战），阶段 2 的绝对成本更低，
  P1 的比值可能比 7.3× 温和。**这不否定结论，但限制外推。**
- **模型时效**：跑的时候模型版本可能与 2026-09-10 不同。
- **执行者与判定者分离**只降低了自证风险，不能消除——陷阱是本仓库设计的，
  设计者知道答案。缓解：判据只看**交付物内是否有指向外部源的证据**，
  不看"是否猜到了陷阱"。
- **成本口径**：`cost-report.mjs` 统计整个 session（含追问轮）。若中途有额外追问，
  两 arm 必须追问次数相当，否则记入局限。

**读数修正（重要）**：终态放大倍数 **147.1×** 而非中途快照的 106×——差额花在

P2 的阈值 ≤150× 只**勉强**通过，而那段开销正是抓到 2 个 CRITICAL 的机制。
**下一轮该讨论的不是"值不值"，而是"验证成本能否按风险分级"**（低风险判据抽样）。

**初步读数（待 standard 臂补齐后按 §1.5 判定）**：

1. **成本侧 `P2` 通过（106.0× ≤ 150×），且相对旧 xdev 是数量级改善**：
   放大倍数 346× → 106×，已回到 standard 的量级（107×）。这正是阶段 2 信封与
   轮次纪律要治的病，读数支持"刹车生效"。
2. **subagent 从 24 → 4**（阶段 2 从 12 → 2），信封未被突破。
3. `P3`（首个实现 ≤6min）在标准档 ✅ 通过（5.2 min）。
4. `P1`（总 token ≤3× standard）**暂不判定**——依赖 standard 臂读数；
   若 standard 落在 15–35 M，则比值约 0.5–1.1×，远优于 3× 目标。
5. **`Q2` 陷阱② 已由独立证据确认可判定且机制有效**：该臂的 `acceptance.py --selftest`
   在中间态**自己报出 A19 FAIL**（"判据 A11 没有任何变异探针（不可伪证）"）
   与 **A20 FAIL**（`report.md` 不存在）——然后修复，最终 **20 条判据全 PASS、缺项 0**。
   即：假绿被它自己的自证伪检查抓住，而这条要求是 prompt 强制项，**两臂同条件**。
6. 阶段 2 上下文占比 42.5% **高于**信封的 ≤25%——说明该上限对本任务过严，
   或该臂在计划阶段偏重。按 skill 的兜底条款，这属于"阈值可能定错"的信号，
   **应改阈值而非改任务**（已记入本实验的结论待办）。

### 4.1b 我的独立复核发现一处**存活缺陷**（该臂自报 20/20 全绿）

交付物自称"对抗审查抓到 2 个 CRITICAL（`next` 谎报不可达；星期 `~` 绕过 7≡0 归一），
全部已修并各自补判据与变异"。我逐条复核：

- **CRITICAL-1 确已修复** ✅：`next "0 0 29 2 *" 25` → stdout 24 行 + stderr 说明 + rc=4，
  不再把"n 超窗口容量"谎报成"永不触发"。
- **CRITICAL-2 未真正修复** ❌：`0 0 * * ~` 给出的是**周一**（01-05/01-12），
  而 `0 0 * * 0` / `7` / `SUN` 都正确给出周日（01-04/01-11）。
  规范第 220–226 行说 `~` 在字段范围内随机取值（dow 为 0–7，且 7≡0）。

**为什么它自己的 20/20 与 31 对探针没抓到**：它的判据只覆盖了**`7~7` 这个形态**
（`("0 0 * * 7~7", "0 0 * * 0")` 等价性），**没有覆盖裸 `~`**。
于是针对 `~` 的变异 `m_tilde_dow_unnormalized` 只在 `7~7` 上被触发，裸 `~` 路径漏过。

**这条对实验结论的意义（必须写清）**：修正 §4.1 第 5 条的措辞——
陷阱② 的机制**部分有效**：它确实抓住了"某条判据没有探针"这种**元层面**的假绿
（A19），但**抓不到"判据覆盖不全"**（只测 `7~7`、漏 `~`）。
这正是我在优化方案 §2.3 里称为"**只修实例、不清类**"的同一类问题，
只不过这次发生在**测试覆盖**上而不是源码上。**我之所以能发现，是因为我没有采信它的
自述，而是自己敲了命令。** 这也再次印证方案 §1.5 要求"判定由第二方做"的必要性。

### 4.1c 一条比读数更重要的流程发现：门禁**拒绝**了"自报已修"

该臂在收尾时主动更正了一条**自己的不实陈述**：它先前汇报"第 2 轮复核 reject 的 5 条
已逐条修复"，而实际 **D5（design.md 的 Must Not 行与 F9 自述自相矛盾）声称已改但未改**
（补丁脚本漏了那条替换）。是第 2 轮复核的 fresh subagent 用全量 grep 独立证实的。

**我的独立复核（4 项全部与它的更正一致）**：

| 检查 | 结果 |
|---|---|
| design.md / plan.md 哈希 | `f3d1d199…` / `2521ae7bad…` —— 与声称逐字一致 ✅ |
| cronspec.py / acceptance.py / report.md 哈希 | `2b21fb66…` / `a25cda82…` / `0475028e…` —— **代码零改动属实** ✅ |
| 变异标识集合双向差集 | plan 29 个 vs `Mutant("m_…")` 29 个，**两个方向都为空** ✅ |
| 被指出的两处文档残余 | A5 行已含"超长数字 rc=1 且无 Traceback"；探针表已补 `m_unguarded_int` ✅ |

**对机制的两条相反证据，必须同时记下**：

1. **❌ 又一次"声称 vs 实际"失真，而且发生在同一个会话里第二次**（第一次是 `~` 星期路径
   谎报已修）。这与 `坦克大战3` 终态 17 处文档失真是**同一类**，也与优化方案 §1.1/§2.3
   的结论一致：**这类缺陷在 xdev 里会被反复抓到，但也会被反复重新引入**。
2. **✅ 但这次它被抓到了，而且门禁没有放行**：抓到它的是第 2 轮 fresh 复核（全量 grep），
   不是自审；并且——关键——**该臂明确拒绝把未返回的最终裁决写成通过**：
   *"其最终裁决尚未返回……若未返回，交付报告按『最终确认未取得』记录，不按『已通过』处理。"*
   这正是硬规则 3 的字面要求（`missing` 计未知、维度不全不得 approve）。
   **在 v3.1 之前，一条挂死的审核员会被静默当作"审核完毕"**（实盘证据：A3 挂死 5 分钟，
   编排层直接宣告审核完成）。这条规则**在真实运行里生效了**。

**结论**：`Q3`（死模块/自证类缺陷的检出）由第二方证据支持 ✅；但同时证明
**"文档声称失真"是 xdev 目前的盲区**——它能抓住，却挡不住复发。
下一轮优化应把 §2.3 的漂移比对**做成交付前的阻塞项**（本臂的 `report.md`/`DELIVERY.md`
完全可被 `.xdev/drift.json` 式机械核对，但目前没有把它接进阶段 4）。
